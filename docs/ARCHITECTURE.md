# Architecture

Reviewed and agreed on 28 September 2026. Record every later change here, with its reason, before coding it (see §9 Decisions).

Runtime: Next.js 16 (App Router, Turbopack build), React 19, TypeScript strict, Tailwind 4. Code must run on **Node 20.9+** (`engines` in package.json). Local development uses Node 24, and the host will likely offer 20 or 22, so avoid Node APIs newer than 20.9.

## 1. Shape
One Next.js app. No separate backend. The storefront and the panel share one codebase and one database:

```
Browser
  |-- Storefront   (public pages, cart, checkout, confirmation, tracking)
  |-- Panel        (/panel/*  admin + developer, menus built from permissions)
  v
Next.js server (Passenger on cPanel, standalone build, pages rendered per request)
  |-- Server Components  : read data for pages
  |-- Server Actions     : mutations (cart quote, checkout, order actions, CRUD)
  |-- Route Handlers     : /api/health
  |                        /media/[...path]                  public product/category images
  |                        /api/checkout/proof               bank-transfer screenshot before the order (signed token)
  |                        /api/files/proof/[id]             payment proofs, permission required
  |                        /api/orders/[orderNumber]/proofs  customer proof upload (delivery charge, re-upload)
  |                        /api/panel/uploads                panel image upload
  v
features/*/service  ->  features/*/repo  ->  server/db (Drizzle + mysql2)  ->  MySQL / MariaDB
                    \->  server/storage (sharp)  ->  UPLOAD_DIR on disk (outside the app folder)
```

## 2. Layers and rules
| Layer | Location | Allowed to | Not allowed to |
|---|---|---|---|
| UI | `src/app`, `src/components` | call services, render | touch DB, contain business rules |
| Service | `src/features/*/service.ts` | business rules, permissions, transactions | render UI |
| Repo | `src/features/*/repo.ts` | DB queries via Drizzle | business rules |
| Pure logic | `src/features/pricing/pricing.ts`, `src/features/orders/status.ts` | calculations on plain data | touch DB or I/O (so unit tests need no DB) |
| Server infra | `src/server/*` | env, db client, session, storage, mail, rate limit | know about features |

## 4. Key flows

### 4.1 Price calculation (`features/pricing`)
- `pricing.ts` is pure. `calculateCart({ lines, discounts, couponCode, coupon, zone, country, flags, now })` prices every line through `priceVariant` and returns the lines (base and effective unit price, line total, line discount), `subtotal` (Σ base price × quantity, before any discount), `discountTotal`, the coupon result (`none`, `applied` with its amount, or `rejected` with a reason code and message), `couponDiscount`, `goodsTotal` (subtotal − discounts − coupon), shipping (`pending` or a priced amount), `total` (goods total plus shipping only when priced) and `codAvailable`. `service.ts` (`priceCart`) loads the discounts and the coupon row and calls it; `features/pricing/display.ts` formats amounts for the UI. The cart quote and `createOrder` both go through `priceCart`. The browser only ever sends **variant ids**, quantities and a coupon code — never a product id directly and never a price; the quote's Zod schema strips anything else, so a fake unit price or total in the request has no effect.
- **Cart quote (S6):** `features/cart/service.ts` validates the browser's cart, loads the variant rows (any status), **reconciles** them (`quote.ts`, pure: duplicate ids merged, unknown/inactive/sold-out variants dropped, quantities capped at stock, each change reported as a notice), prices through `priceCart` and returns display strings plus what the browser should now store (the fixed lines, and the coupon code only while it applies). **Destination (S14):** the checkout sends the country and city it currently shows (`cartQuoteRequestSchema.destination`, re-quoted whenever they change) and the quote resolves the zone with the same `resolveShippingZone` `createOrder` uses, so a `flat` zone's charge is in the summary and in `expectedTotal` before Place order; the cart page and drawer send no destination, so their shipping stays pending — and so does every `quote` zone's, exactly as before S14. Coupon attempts are rate-limited per IP (10 per 15 minutes, MySQL bucket `coupon:ip:*`); a successful application resets the bucket, so a customer reloading with a valid code is never blocked while guessing is. The coupon field itself sits in the checkout order summary (S7, `components/store/cart/CouponForm.tsx`); the cart page and drawer only show an applied coupon as a totals row.
- **Money:** integer paisa inside the module. `money.ts` converts to and from DECIMAL strings and formats (`formatMoney()`). PKR amounts from percentages are **rounded to whole rupees**, half up.
- **Variant pricing:** a line's base unit price is `variant.price_override` when set, else the parent product's `price`. Stock, weight and the SKU/label snapshot all come from the variant; only the discount lookup goes through the parent product.
- **Discounts:** discounts target a product, a category or the whole store, never a single variant — a matched discount applies to every variant of that product, computed against that variant's own base price. The single discount giving the lowest unit price wins, chosen per variant (with a percent and a fixed discount both matching, a cheap variant can get the fixed one and a dear one the percent). Ties go to the lowest discount id. A percentage's amount is rounded to whole rupees, half up, before it is subtracted. The `discounts` flag in `config/features.ts` turns all discounts off. `pricing/service.ts` loads the switched-on discounts once per request (React `cache()`) and prices every variant on a page against one `now`. Discounts never stack. A fixed amount is per unit, clamped at 0. A `category` target matches the product's category or that category's parent. A discount is active when `is_active` is set and `starts_at <= now < ends_at` (null bounds are open).
- **Exclusivity (cart-level, confirmed):** a line is discounted when its effective price is below its base price. If any line is discounted, the coupon is rejected with `COUPON_BLOCKED_BY_DISCOUNT` ("Coupons cannot be combined with discounted items."). The cart then removes the stored code and shows the message.
- **Coupons:** the code is case-insensitive (trimmed, uppercased; stored uppercase). The coupon must be active and within its dates (`starts_at <= now < ends_at`). `min_order` is compared with the subtotal. A percentage is rounded to whole rupees and capped by `max_discount`. A fixed amount is clamped to the subtotal. Coupons never reduce shipping. Both usage limits are checked in `pricing.ts`: the total one against `used_count`, the per-customer one against this customer's `coupon_usages` count (keyed by the normalised phone), which `pricing/service.ts`'s `loadCoupon` fetches whenever the phone is known. The checkout sends the phone with its quote requests (`cartQuoteRequestSchema`), so a customer who has used the code up sees it dropped as soon as they enter their number; `createOrder` repeats the check under lock. Checks run in this order: exists, active, dates, total usage limit, per-customer limit, exclusivity, min order.
- **Shipping (client decision: quote only):** every zone (Karachi, Pakistan, International) runs in `quote` mode with `flat_rate = 0` for the first release, so the pricing result is always `pending` until staff set a charge — the cart and checkout total shown is the goods total, with "Delivery charge: to be confirmed, we will contact you on WhatsApp" (`siteConfig.deliveryPendingNote`). The cart quote passes no zone at all (the address isn't known yet), which is also `pending`. `flat` mode (optionally with `free_over_amount`, compared with the goods total after discounts and coupon) exists in the data model and is unit-tested in `pricing.ts` for a future zone switch, but nothing seeds or exercises it today. **COD** requires the `cod` flag on, the zone's `cod_enabled`, **and** `country === 'PK'` (`isCodAvailable`) — the country check is a hard rule enforced again in `createOrder`, independent of zone configuration, so an edited request can never buy COD outside Pakistan.
- **Currency:** PKR is always computed first and is also what's shown — `multiCurrency` is off and out of week-1 scope entirely (no switcher, no exchange-rate input anywhere in the UI). The columns exist so a future client can flip this on without a schema change.

### 4.2 Place order (`checkout/createOrder`)
The checkout page (`components/store/checkout`) sends: a `checkoutToken` (a UUID the browser keeps in `sessionStorage` until an order is placed, so a resubmit after a lost response returns the same order), the contact and address fields, the payment method, for bank transfer the `proofToken` from the screenshot upload (§4.4), the cart's variant ids and quantities, the coupon code and the quote's `expectedTotal` (a DECIMAL string the quote returns for exactly this purpose). The form validates with the same Zod schema the server uses (`checkout/schemas.ts`), so mistakes show without a round trip. Phone numbers are normalised by `lib/phone.ts` (pure, tested): `03XX…`, `+92 3XX…`, `92 3XX…` and `0092 3XX…` all become `923XXXXXXXXX`; any other number keeps its digits with the country code; a local number without a code outside Pakistan is refused. The stored form is what `/track` compares and what the coupon per-customer limit keys on.
1. Validate input with Zod. Check the rate limit (10 per IP per 15 minutes, bucket `checkout:ip:*`). Phone is required, email optional.
2. If an order with this `checkout_token` exists, return it (idempotent re-submit). Two submits racing past this check meet the unique key inside the transaction; the loser looks the order up and returns it too.
3. Refuse COD unless `country === 'PK'` (the hard rule, before any zone is consulted). For bank transfer, refuse without a `proofToken` ("Please upload your payment screenshot…") or with one whose signature or expiry fails ("…has expired. Please upload it again."); both come back as a `proofToken` field error, so the form restarts its picker (owner decision, D32). Resolve the shipping zone from country + city (`shipping/zones.ts`, pure: exact city, else whole country, else the fallback zone; the checkout city picker offers Karachi / other city in Pakistan). No zone at all is refused.
4. Start the transaction. `SELECT … FOR UPDATE` the **variant rows only**, **in ascending variant id order** (locking through the product join would lock products and categories too); then read their products and categories without a lock. If there is a coupon, `loadCoupon(…, { db: tx, lock: true })` reads its row under `FOR UPDATE` together with this customer's usage count.
5. Recompute with `priceCart` using the locked rows. If an item's product is inactive, or the variant is inactive or out of stock, fail with a clear message naming the item. If the coupon is rejected for any reason, fail with its message. If COD was chosen and `codAvailable` is false, refuse. If the total differs from the client's `expectedTotal`, fail with "Prices changed, please review your order before placing it." Nothing is written in any of these cases.
6. Insert the order. `order_number` = `RSH-YYMMDD-XXXX` (`checkout/order-number.ts`, prefix from `site.config`): the Karachi date plus 4 characters from `23456789ABCDEFGHJKMNPQRSTUVWXYZ` drawn with `crypto.randomInt`, retried inside the same transaction on a duplicate key (up to 5 times). Then insert the items with product id, variant id, name/variant-label/SKU snapshots (the label is `""` for a simple product's "Default" variant) and price snapshots (base unit price, per-unit discount, line total).
7. Decrement the **variant's** stock. If a coupon was used, insert `coupon_usages` (customer key = normalised phone) and increment `used_count`. For bank transfer, move the pending screenshot to `proofs/YYYY/MM/<name>.webp` (a missing file — already used, or swept — refuses the order with the expired message) and insert its `payment_proofs` row (purpose `goods`, status `submitted`, relative path, file size). The move is the last write before the history rows: if the transaction fails before it, the pending file simply stays; if it fails after, the file is moved back to `pending/`, so the deadlock retry or the customer's next submit can still use it (the 24-hour sweep deletes it otherwise).
8. Set `payment_status` from the payment method regardless of zone mode: bank → `proof_submitted` (the screenshot came with the order); COD → `cod_pending`. Set `order_status`: a `quote` zone (every zone today) always starts `awaiting_shipping_quote`, with `shipping_total` and `shipping_note` left `NULL` until staff set the quote (AD-03); a `flat` zone (not used at launch) starts `pending` directly with `shipping_total` set. `display_currency`/`exchange_rate`/`display_total` are `PKR`/`1.0000`/`total`.
9. Insert two `order_status_history` rows (kind `order`: → order status, note "Order placed"; kind `payment`: → payment status, note "Payment screenshot uploaded at checkout" for bank), then commit. On deadlock (errno 1213), retry the whole transaction once.
10. The Server Action grants the order-access cookie and returns the order number; the browser clears its stored cart and its checkout token, then navigates to `/order/[orderNumber]`. After the response, via `after()` (never inside the transaction, never blocking the order): a web-push notification to every subscribed owner device for "new order placed" (S21; payload carries only the event type and the order number, never the customer's name or phone); the customer's "order received" email, only if they gave one; the owner's new-order email, only if `notify_owner_order_emails` has recipients (off by default — push is the primary alert). A later delivery-charge screenshot upload and a new wholesale inquiry fire the same two channels (push always, email per its own setting) from their own service functions, not from `createOrder`. Every mail or push failure is logged (`audit_logs`, action `notify.failed`) and never fails the triggering action.

### 4.3 Order status machine and the panel's orders workflow (`orders/status.ts`, `orders/transitions.ts`, pure and tested)
- Order: `awaiting_shipping_quote → pending | processing | rejected | cancelled` (approving with a delivery charge above zero paid by transfer goes to `pending`; a zero charge, COD, or `deliveryChargeByTransfer` off goes straight to `processing`); `pending → processing | rejected | cancelled` (once every due payment is verified); `confirmed → shipped | delivered | rejected | cancelled` and `processing → shipped | delivered | rejected | cancelled` (fulfilment can skip `shipped` straight to `delivered`); `shipped → delivered`. Cancelling or rejecting is allowed until `shipped`. **`confirmed` is no longer entered** (owner decision, D36): an order approved before S9 that is still `confirmed` reads as Processing everywhere; the enum keeps the value so old rows need no migration.
- Payment: `unpaid | rejected → proof_submitted` (upload); `proof_submitted → verified | rejected | unpaid` (the last when the products screenshot is approved and the delivery charge is now due); `verified → unpaid` (the delivery charge is set on an order whose only due payment was already verified); `cod_pending → cod_collected`.
- **Two payments per bank order (owner decision, D32).** The goods are paid at checkout and the delivery charge after staff set it, so each `payment_proofs` row has a `purpose` (`goods` | `delivery`) and each payment's state is its **latest** proof's status (`missing` when none). `orders/status.ts` derives this (`paymentProgress`, pure and tested): the delivery payment is `awaiting_charge` while `shipping_total` is NULL, `not_due` for a zero charge or while `deliveryChargeByTransfer` is off (option B: delivery charge in cash on delivery). The customer page, the timeline and the upload route all read that, never `payment_status`. `orders.payment_status` is the order-level summary staff filter on: a bank order is created `proof_submitted`, and every customer upload sets `proof_submitted`. **`recomputePaymentStatus` (S9)** runs after each review and when staff set the delivery charge: `verified` when every payment due has a verified latest proof, `rejected` when a due payment's latest proof was rejected and nothing awaits review, `unpaid` when a due payment has no proof (the delivery charge right after staff set it), else `proof_submitted`. So the goods can be `verified` while the order still awaits the charge, and the order drops back to `unpaid` when the charge is set; "can't move to `processing` until `verified`" then means both payments are in (`statusAfterPaymentReview`).
- Moving into `cancelled` or `rejected` (reason required for rejected) restores stock (`stock_restored_at`, so a second attempt is a no-op) and **releases the coupon use** (the usage row is deleted and `used_count` decremented) in the same transaction. This happens once only, because the state machine forbids leaving those states. **Rejecting a payment screenshot rejects the order the same way** (owner decision, D37): `reviewProof`'s reject branch and `closeOrder` share this mechanics (`closeOrderTx` in `staff-actions.ts`).
- Unpaid bank orders hold their stock until staff cancel them. Nothing expires automatically.
- Every change writes `order_status_history` (user, time, note). Internal notes are history rows with `kind = 'note'`.

**The panel's queues (owner decision, D36).** Two pages, one per payment method (`/panel/orders/bank`, `/panel/orders/cod`), each with the same tabs over the two enums above: **Need review** (`awaiting_shipping_quote`, plus a COD order left in `pending` by hand — the flow never produces that, but an old or manually-edited row still has to show somewhere); **Pending delivery charge** (bank transfer only: `pending`); **Processing** (`confirmed` and `processing`); **Delivery** (`shipped`); **Completed** (`delivered`); **Cancelled**; **Rejected**. `orders/transitions.ts` (`orderTab`) states this mapping once as plain data; `staff-repo.ts`'s `TAB_CONDITIONS` states the same rule in SQL, and `staff.integration.test.ts` checks every enum combination lands in exactly one tab.
- **Approve order** (`approveOrder`, one transaction): sets the delivery charge and note, approves the products screenshot if it is still `submitted`, and moves the order on (`approvedStatus`). Refused (`approvalRefusal`) unless the order is `awaiting_shipping_quote`, and, for a bank order, unless its products screenshot is `submitted` or already `verified`.
- **Reviewing a screenshot** (`reviewProof`) approves or rejects (reason required) whichever screenshot is `submitted`, in any open tab — not only Need review — except a bank order's *products* screenshot while the order is still `awaiting_shipping_quote`, which only "Approve order" touches (`canReviewProof`, `screenshotsToCheck`). Approving recomputes `payment_status` and, once every due payment is verified, moves a `pending` order on to `processing`, so an order is never stuck in Pending delivery charge behind a screenshot that was already approved. **Rejecting rejects the whole order instead** (owner decision, D37, replacing S9's original "stays open, upload again"): in the same transaction the proof is marked `rejected` with the reason, `order_status` becomes `rejected`, `payment_status` is recomputed (also `rejected`), stock is restored once and the coupon use released, exactly as `closeOrder` does for a manual reject. The customer sees the order as Rejected with the reason and can never upload another screenshot for it (`uploadPurpose` only ever asks for a `missing` screenshot, never a `rejected` one, and an order that isn't `awaiting_shipping_quote` or `pending` takes no uploads at all). Needs both `order.verify_payment` (to review the screenshot) and `order.update_status` (to close the order); approving needs only the first.
- **Fulfilment** (`updateFulfilment`): Processing can move to `shipped` and/or `delivered` directly (skipping Delivery); courier and tracking note are optional; delivering a COD order also sets `payment_status = cod_collected`.
- **Close** (`closeOrder`): cancel or reject (reason required) until `shipped`, as above.
- **The panel UI** (`components/panel/orders`): a coloured status pill (`StatusMenu`) opens a popover of only the moves `control.actions` allows — never the current or an earlier tab — Cancel/Reject last below a divider; choosing one opens its dialog (`OrderDialogs`), and nothing changes until the dialog is confirmed. The trash icon (`trashActionForTab`, D38) opens the same Cancel/Reject chooser while the order is still open, a permanent delete confirmation once it's Cancelled or Rejected, and nothing once it's out for delivery or completed. Every action runs through the same Server Actions (`app/panel/(protected)/orders/actions.ts`) whether opened from the list or the detail page.
- **The list pages** (`OrdersPageBody`): tabs and the search box render immediately from `getOrderCounts` (cheap, independent of the tab/search/page); the table and its pagination sit in their own `<Suspense>` (keyed on tab/search/page, `OrdersTableSkeleton` as the fallback), so switching tabs, searching or paging only ever re-shows a table-shaped skeleton behind the tabs, never the whole page. `loading.tsx` on the list and detail routes covers the cold-navigation case, before even the tabs are known. `Pagination` shows "Showing X–Y of Z", numbered pages with an ellipsis for a long run, and redirects to the last page when the requested one is past it.
- **The detail page** (`/panel/orders/[bank|cod]/[orderNumber]`, `OrderDetailView`, redesigned in the same slice against an Eyeazy-style reference): the header bar shows only a breadcrumb (`Orders – Bank transfer / RSH-…`, via `PanelPageTitle`); the page itself has the title once, in one row with the back arrow, the status and payment pills and the placed date, and — on the right of that row — the same `control` used for the pill: one primary button (the first forward action) plus a ⋮ menu (a proper three-dot icon, not the hamburger rotated) for Cancel/Reject — neither shows once the order is closed or completed. Below, two columns (about 2:1 on `lg`, the customer card first when they stack on phones): left, in order, Items, a highlighted review card when a screenshot needs checking (`TopAlertCard`/`ScreenshotReview`, sharing the list's dialog; a bank order in Need review with a `submitted` products screenshot shows that instead, next to a "Reject order" link into the Approve dialog's reject mode; failing both, a plain message and a WhatsApp button while the order simply waits on the customer), Payment screenshots (small ~64px thumbnails, click to enlarge — `ProofImage`), Delivery (only the rows that have a value; before approval, one line saying the charge is set on approval), Payment summary (a highlighted total row) and Activity; right, the Customer card (avatar, a full-width labelled WhatsApp button, contact, address, note).

### 4.4 Payment screenshot
Owner decision (D32): a bank-transfer customer pays the **products total** and uploads its screenshot **at checkout**, before the order exists; the delivery charge follows as a second screenshot once staff set it. Server Actions cap bodies at 1 MB, so the checkout upload is a Route Handler in two steps (D33). Every zone is quote-only today; a zone switched to `flat` later (S14) would still take the delivery charge as a second payment, so revisit this then.
- **Checkout upload:** `POST /api/checkout/proof` (Route Handler). Same-origin `Origin` check and the size checks below, then a rate limit (10 per IP per 15 minutes, bucket `proof:ip:*`, shared with the order-page upload) before the body is read. The re-encoded file goes to `UPLOAD_DIR/proofs/pending/<random>.webp` and the response is `{ token }`: a base64url `{ f: file name, e: expiry }` signed with HMAC-SHA256 under `SESSION_SECRET` (`payments/proof-token.ts`, pure and tested; signed under a label so an order-access cookie value never passes as one), valid for **1 hour**. The file name must be 32 hex characters, so a token can never name a path. Each checkout upload first deletes pending files older than 24 hours (abandoned checkouts). `createOrder` exchanges the token for the file inside its transaction (§4.2 steps 3 and 7); one upload pays for one order, since the move consumes it.
- **Checkout UI:** with Bank transfer selected, below the bank details: the amount to transfer now (the quote's `goodsTotal`, with a copy icon), the delivery-charge note, and the required screenshot picker (`components/store/orders/ProofUpload.tsx`: `accept` jpeg/png/webp and no `capture`, so phones offer the photo library; a local preview; XHR upload progress; the server's messages). Place order stays disabled until the upload returns its token. If the goods total changes after the upload (a coupon applied), a notice asks for a matching screenshot.
- **Order-page upload:** `POST /api/orders/[orderNumber]/proofs?purpose=goods|delivery`, from SF-06. Requires the order-access cookie, the same Origin and size checks, and rate limits per IP and per order (5 per hour, `proof:order:*`). The server accepts it only when `uploadPurpose()` (§4.3) says that purpose is due: the order is `awaiting_shipping_quote` or `pending`, the payment method is bank transfer, and that payment's latest proof is missing — for the delivery charge also the charge is set and above zero and `deliveryChargeByTransfer` is on (so the delivery upload is refused while `awaiting_shipping_quote`, PAY-06). A `rejected` proof is never due for upload again (D37): rejecting one rejects the whole order in the same transaction, so by the time a proof is `rejected` the order is already closed and `uploadPurpose` refuses on the order status alone. The goods come first if both are due. At most 5 proofs per order. The check runs before processing and again under `SELECT … FOR UPDATE` on the order row. The file is written first (temp file, then renamed to `proofs/YYYY/MM/<random>.webp`) and deleted if the transaction refuses or fails; the row is inserted with its purpose, and the order moves to `proof_submitted` (a `payment` history row, or a `note` row when it already was).
- **Validation:** reject when `Content-Length` is missing or > 5.5 MB before reading the body, then check the file part ≤ 5 MB. The real type comes from `sharp().metadata()` (magic bytes): jpeg, png or webp only. Images over 25 megapixels are refused from the header, before any decoding, and `limitInputPixels` guards the pipeline too.
- **Processing** (`server/storage/images.ts`): `.rotate()` (applies EXIF orientation), resize so the longest side is ≤ 2000 px, WebP output with no metadata. sharp runs with concurrency 1 and cache off. Paths are stored relative to `UPLOAD_DIR` (`server/storage/proofs.ts`); `env.ts` refuses to start when `UPLOAD_DIR` is not an absolute path outside the app folder.
- **Order page (SF-06):** where each payment stands (products, delivery charge); once the charge is set, "Pay the delivery charge of PKR X" with the bank details, amount and copy icons and the upload. With `deliveryChargeByTransfer` off it says to pay the delivery charge in cash on delivery instead.
- **Serving:** `/api/files/proof/[id]` needs a panel session with `order.verify_payment` or `order.view` (`authorizeRequest`: 401 without a session, 403 without either permission). It looks the path up by id (never a user-supplied path), checks it resolves inside `UPLOAD_DIR/proofs`, and sends `Cache-Control: private, no-store`, `X-Content-Type-Options: nosniff`, `Content-Type: image/webp`.
- **Review (S9, D37):** approve (`verified`), per proof; staff see each proof's purpose. **Rejecting rejects the whole order** (owner decision, D37): the customer sees it as Rejected with the reason and there is no re-upload — see §4.3.

### 4.5 Auth, permissions and order access
- **Passwords:** `node:crypto` scrypt with a random salt, compared with `timingSafeEqual`. No native module.
- **Sessions:** a random 32-byte token in an HTTP-only, Secure, SameSite=Lax cookie. The DB stores its SHA-256 (`sessions.id`). Expiry is 7 days absolute, and `last_seen_at` is updated at most once an hour. Logout or deactivating a user deletes the sessions. Login is rate-limited by IP and email.
- **Permissions:** `requirePermission(key)` sits at the top of every panel page, action and route. `key` is typed from the `PERMISSIONS` const. The user's permission set is loaded once per request (React `cache()`). The sidebar is built from the same set. The code never checks role names.
- **Seed and the system roles (revised again, S20, owner decision BUILD_PLAN.md C34 amending C24):** the seed is idempotent. It upserts the permission rows from `PERMISSIONS` and creates `developer`/`admin` (`is_system`) **once, with their code defaults**; after that it only grants a *brand-new* permission key (one it inserted into `permissions` for the first time) to whichever role's default list names it, and it **never revokes or re-grants** anything on an existing role (`features/auth/seed-roles.ts`, `grantRolePermissions`). The code defaults are therefore the first-run starting point only; the live sets belong to the panel's permissions matrix (`/panel/roles`), which can toggle any key on any role, system roles included, and offers "Reset to defaults" per system role. Between S9b and S20 the seed synced by granting *and revoking*; that would now silently undo a panel edit, so it's gone. `is_system` roles can't be deleted in the panel (the seed and the users page rely on them existing).
- **Landing page by permission (S9b):** after login, a user is redirected to the first page their permissions allow, in a fixed priority order (dashboard → orders → wholesale → products → settings → users → roles → audit); the Developer no longer holds `dashboard.view`, so `/panel` (the dashboard) is never their landing page — they land on `/panel/products` instead. The 403 page links to that same first-allowed page rather than to `/panel`.
- **Users, roles and the audit viewer (S20, D59):** `/panel/users` (`user.manage`), `/panel/roles` (`role.manage`) and `/panel/audit` (`audit.view`), all Developer-held by default (C24). Deactivating a user, changing their role, or resetting their password deletes every `sessions` row of theirs; saving any role deletes its members' sessions (the editor's own stays). Because `getSession` re-reads the permission set from `role_id` on every request, a role or permission change would apply on the user's next request even without that — the revoke just forces a clean re-login. Every gate in the app checks a permission key per request, never a role name, so the live sets may overlap freely (the Admin can be given `product.view` and the products nav item, page and actions simply appear for them); only the *default* sets in code are asserted disjoint (`permissions.test.ts`).
- **Change password (S9b, owner decision BUILD_PLAN.md C25):** any signed-in user, no permission key needed, from `/panel/account`. Zod schema requires the current password, a new one ≥ 8 characters that differs from the current, rate-limited per user; checked against `password.ts`'s scrypt helper. On success every other session row for that user is deleted (the current session's row stays) and an `audit_logs` row is written (`action: 'user.password_change'`, no secrets in `old_values`/`new_values`).
- **Order access (customers):** the `order_access` cookie (HTTP-only, SameSite=Lax, Secure in production, 30 days): a base64url JSON payload of up to 20 order numbers (newest first) plus an expiry, signed with HMAC-SHA256 under `SESSION_SECRET` (`checkout/order-access.ts`, pure and tested; `order-access-cookie.ts` reads and writes it). It is granted by placing an order, or by `/track` verifying order number **plus the phone number used at checkout** (10 lookups per IP per 15 minutes; a miss says only "not found", never which half was wrong; no email-based lookup, since email is optional at checkout and may be absent). A successful lookup redirects to `/order/[orderNumber]` (SF-06), which doubles as the confirmation page and reads live from the database. Without the cookie that page redirects to `/track?order=…`. That page and proof upload require the cookie.
- **CSRF:** Server Actions use Next's built-in Origin check (`serverActions.allowedOrigins` from `APP_URL`). Route Handlers that change state check `Origin` themselves (`isAllowedOrigin` in `server/request.ts`, against `APP_URL` and `ALLOWED_ORIGINS`; a missing `Origin` is refused).
- **Client IP:** the last `X-Forwarded-For` entry, which is the one appended by Apache/Passenger.

### 4.7 Admin dashboard (S16, owner decision BUILD_PLAN.md C28, replacing REQUIREMENTS AD-04)
- Route `/panel` itself (Admin only, `dashboard.view`; not a `/panel/dashboard` subroute — it doubles as the Admin's landing page, §4.5). A period selector (Today, 7 days, 30 days, This month, All time; default 30 days; kept in the URL as `?range=`, Zod-parsed with an unknown value falling back to the default) resolves to a `[from, to)` pair on **Asia/Karachi day boundaries** (`dashboard/ranges.ts`'s `resolveRange`, pure). `from` is the Karachi midnight of the period's first day; `to` is simply `new Date()` at the moment each block resolves its own range — **not** memoized through React's `cache()`, because `cache()` only resets at a real Next.js request boundary: called directly (as the integration tests, and any future script, do) it freezes "now" at whichever call reached it first, which silently excluded that instant's own orders from every later query in testing. The few milliseconds' difference between this page's blocks each calling `new Date()` separately doesn't matter at day-level granularity.
- Four stat cards (Revenue with a pending-revenue sub-line, Total orders, Average order value, Total wholesale leads), each paired with the previous period of the same length (`previous = [from − length, from)`, uniformly — so "Today" compares against yesterday's same elapsed portion of the day, not all of yesterday) for a change badge — except All time, which has none. The badge is "new" rather than a divide-by-zero infinity when the previous period was empty but the current one isn't, and "zero" when both are empty (`computeChange`, five states, unit-tested). Definitions (owner decision, 2 Oct, refining REQUIREMENTS §6.2): **Revenue** and **Pending revenue** both sum the order's *goods price only* — `subtotal − discount_total − coupon_discount` (`dashboard/repo.ts#goodsTotalSql`), never the delivery charge, even once one has been added to `orders.total` — for non-cancelled orders with `payment_status` in (`verified`, `cod_collected`) and for non-cancelled/non-rejected orders not yet in those states, respectively; the delivery charge is a pass-through logistics cost, not sales revenue. Total orders excludes `cancelled` and `rejected`. Average order value is the mean `total` (goods **plus** delivery charge, once set — what the customer actually paid) of those same orders, a dash when there are none — so AOV and Revenue intentionally read different bases; see D46. Wholesale leads counts `wholesale_inquiries` created in the period. Every one of these is one SQL query with conditional `SUM`/`COUNT` (`dashboard/repo.ts#getOrderAggregates`), filtered on the indexed `orders.created_at` — `EXPLAIN` against the seeded dev data (130 rows) shows MySQL choosing a full scan over the available index at that size, which is the optimizer working as intended on a small table, not a missing index; the index is there and ready for when order volume grows past the point a scan is cheaper.
- The revenue chart (daily points up to 31 days, else weekly or monthly bins, with order count as a second series on its own independent y-scale) is **plain inline SVG** (`components/panel/dashboard/RevenueChart.tsx`, a small client component only for the hover/tap tooltip) — no charting library, per CLAUDE.md #1 — built from `dashboard/repo.ts#getDailyRevenueSeries` (one `GROUP BY DATE(created_at + INTERVAL 5 HOUR)` query returning one row per Karachi day that had an order, the same goods-only revenue as the stat card) and `dashboard/chart.ts`'s pure, unit-tested `fillDailySeries` (zero-fills empty days) and `bucketSeries` (week = fixed 7-Karachi-day bins, month = calendar Karachi month; both only ever exercised by "All time", since every other range is ≤31 days). The line is a smoothed Catmull-Rom curve (`chart.ts#buildSmoothPath`/`buildSmoothAreaPath`, still passing through every real data point — only the curve between them is smoothed) with a gradient fill under Revenue, matching the owner's reference dashboard; the legend (coloured dots, "Revenue"/"Orders") sits in the card's own header row next to its title, via `DetailCard`'s `action` slot, not below the plot. An accessible visually-hidden `<table>` and `<title>`/`<desc>` carry the same data for assistive tech; one data point or none each get a plain message instead of an unreadable sliver of a chart.
- Most selling products: top 5 by `order_items` units from orders not `cancelled`/`rejected` in the period, grouped by `product_id` (so a product's variants collapse into one row, reading `name_snapshot` off the order item rather than joining `products`), with thumbnail (`features/catalog/repo.ts#getPrimaryImagesByProductId`), name, units and revenue — shown 3 at a time in a `max-h` scrolling list, so this card's height matches the chart card beside it instead of stretching (or leaving blank space) to fit however many rows happen to exist.
- Recent orders: the latest 8 across both payment methods, any status, **not** period-filtered — its own query, always just "the latest 8" — reusing `orders/transitions.ts`'s `orderTab`/`TAB_INFO` and `components/panel/orders/tab-colors.ts`'s `TAB_COLORS` for the status pill, so it never drifts from the orders list's own colours and labels. The whole row opens the order (not just the order-number link, mirroring `OrdersTable.tsx`'s row-click pattern), and a phone-width card list replaces the table below `md`, matching the orders/wholesale lists' own responsive pattern. Two text links out to `/panel/orders/bank` and `/panel/orders/cod`.
- Every figure above is one indexed SQL aggregate, never a per-row loop; nothing here does per-request image or file work. `dashboard.integration.test.ts` prices a hand-computed fixture of orders (known dates, statuses and payment states, including one with a delivery charge already added to `total`) against every definition above, including the previous-period comparison, the most-selling collapse, the chart's day buckets (an order at 23:30 Karachi lands in the correct day, and a day with only excluded — cancelled/rejected — orders buckets to a true zero, not a gap) and that Revenue excludes a delivery charge while Average order value doesn't; permission tests cover an Admin session loading it, a Developer session redirecting to its own landing page, and a no-permission session falling back to `/panel/account`. See D45, D46.
- **Dev data:** `scripts/seed-demo-dashboard.ts` (`db:seed:dashboard`/`db:reset:dashboard`, CLAUDE.md Commands) places ~120 orders and ~15 wholesale inquiries through the real `createOrder`/`createWholesaleInquiry` services, then backdates and advances each with direct SQL to a realistic status mix. Every row it creates carries a `"Dashboard Demo — "` name-prefix tag, so the reset can remove exactly its own rows (crediting back only the stock its still-open orders held, the same `stockRestoredAt` guard the real app uses) without disturbing `db:seed:orders`/`db:seed:wholesale` data placed alongside it. Because ~120 orders need far more stock than these dev variants are seeded with, the script temporarily boosts the handful of SKUs it uses and reverses the exact same amount on reset, so a seed-then-reset cycle leaves the catalogue's real seed stock unchanged.

### 4.8 Wholesale inquiries (S17)
- **Storefront (`/wholesale`, REQUIREMENTS SF-08).** A Server Component page (404s via `notFound()` when `features.wholesale` is off) renders `WholesaleForm` (`components/store/wholesale`), which mirrors `CheckoutForm.tsx`'s pattern: the same `wholesaleInquiryInputSchema` validates client-side before the round trip and again on the server, field errors shown under each field plus a friendly summary banner. Fields: name, optional business name, business type (a `<select>` sourced from `config/site.config.ts`'s `wholesaleBusinessTypes`, not hard-coded in the component), phone (the shared `phoneSchema`), optional email, city, optional needed-by date, repeatable item rows (`WholesaleItemRows`, 1–20 rows: item, quantity, optional note), optional message. A honeypot field (`website`) sits off-screen and `aria-hidden`, with `tabIndex={-1}` — hidden from people and screen readers, so only a bot filling every field reaches it.
- **Needed-by date (owner follow-up, 1 Oct 2026).** `schemas.ts`'s exported `todayInKarachi()` formats "today" with explicit `year`/`month`/`day: "2-digit"` Intl options (forcing zero-padding regardless of ICU defaults — a single-digit day without it would sort wrong against a `YYYY-MM-DD` string) and is called independently on the client (the date `<input>`'s `min`, so the native picker can't offer a past day) and on the server (the same schema), never one trusting the other's clock. A `^\d{4}-\d{2}-\d{2}$` regex rejects a half-typed or malformed value before `Date.parse` ever sees it. The field's own error clears the moment it changes, rather than lingering until the next submit.
- **Spam protection.** `features/wholesale/service.ts`'s `createWholesaleInquiry` checks the `wholesale` feature flag first (defence in depth: the page also 404s, but a direct Server Action call must be refused too), then a per-IP rate limit (`wholesale:ip:*`, 5 per hour — `server/rate-limit.ts`, the same MySQL-backed bucket style as checkout's), then Zod, then the honeypot: a non-empty `website` returns the same `{ok:true}` shape as a real submission but writes nothing and fires no notification — a bot can't tell its submission was dropped.

No order-access-style cookie or customer-facing read path exists for an inquiry (unlike an order): after a successful submission the form is replaced client-side by a thank-you state with a WhatsApp button; refreshing the page just re-renders the empty form.
- **Alerts.** The storefront Server Action (`app/(store)/wholesale/actions.ts`) calls the already-built `notifyWholesaleInquiry(inquiryId)` (`features/notify/service.ts`, S21) via `after()` once a real (non-honeypot) inquiry is stored — never inside the insert, never blocking the response. ## 5. Rendering, images and performance
- Pages are Server Components **rendered per request**, with no data cache and no Cache Components. At about 200 products, indexed queries are cheap. This keeps timed discounts correct, needs no DB during `next build`, and avoids per-process cache drift under Passenger. React `cache()` shares a query within one request. Revisit in the performance pass only if Lighthouse needs it.
- Client Components only where interaction is needed (cart drawer, gallery, forms).
- **Images:** on upload, sharp writes WebP at 400, 800 and 1200 px wide (`<base>-400.webp` and so on) and stores the original width and height. `/media/[...path]` streams them with `Cache-Control: public, max-age=31536000, immutable` (filenames are random and never reused). The path must match `^[a-z0-9/-]+-(400|800|1200)\.webp$`; anything else is a 404. `next/image` uses the custom loader in `lib/image-loader.ts`, which maps the requested width to the nearest variant, so there is no runtime optimiser. Images are lazy-loaded with explicit width and height.
- Every list is paginated. Indexes are listed in DATABASE.md.
- **Shop grid (D27):** the price sort uses the price the card shows (the cheapest active variant's discounted price), which only `features/pricing` can compute. So `/shop` and `/category/[slug]` load the narrow listing columns of every matching active product plus their active variants (indexed on status/category and product_id), price and sort them in memory, then slice one page (12) and load images for that page only. Products with no active variant are left out. Category pages include the category's direct child categories.

## 7. Build and deploy (cPanel)
Owner decision (BUILD_PLAN.md C22, C27): there is no pre-launch client demo, so items 1 and 5 below — making the Linux build actually work, and moving real content onto the host — are **S22 and S23 work**, not a week-1 deliverable; `scripts/build-standalone.mjs` is kept Linux-ready from early on so neither slice starts from zero.
1. **Build on Linux** (GitHub Actions in a private repo — set up in S22; WSL or Docker also work). A Windows build bundles win32 sharp binaries that won't run on the host. `scripts/build-standalone.mjs` is Linux-ready: it runs `next build`, copies `public/` and `.next/static` into `.next/standalone`, then deletes every `.env*` file found there and fails if one remains (SEC-01). Zipping is a manual step. The full checklist is `docs/DEPLOY.md`.
2. **Layout on the host:** the CloudLinux Node selector refuses a real `node_modules` folder in the application root, so the bundle is extracted into a subfolder: `~/rshome/app/` (contains `server.js`, `node_modules`, `.next`). The application root is `~/rshome`, and the startup file is `app/server.js`. `UPLOAD_DIR` is `~/rshome-uploads` (outside both).
3. Set env vars in the Node app screen, never in a file: the bundle ships none, and a local smoke test passes them with `npm run start:standalone` (`node --env-file=.env.local .next/standalone/server.js`). Restart via the panel or `touch ~/rshome/tmp/restart.txt`.
3b. **Security headers (S22, D61):** `src/config/security-headers.ts` holds the production policy (a static CSP with `'unsafe-inline'` scripts and styles but nothing third-party, `frame-ancestors 'none'`, `X-Frame-Options DENY`, nosniff, `strict-origin-when-cross-origin`, a Permissions-Policy, HSTS 180 days without `includeSubDomains`), applied by `next.config.ts` only when `NODE_ENV=production`, so the dev server's HMR is unaffected. Pinned by `security-headers.test.ts` and checked with curl on every standalone build and deploy (DEPLOY.md §7).
4. **Migrations:** `scripts/migrate.ts` (the drizzle-orm migrator) runs from the local machine against the host DB (cPanel Remote MySQL, own IP allowed temporarily), or over SSH if the host offers it. The first migration sets `utf8mb4_unicode_ci` on the database, and the script refuses to run if the database collation differs.
5. **Initial content (S23):** the real catalogue is entered locally through the panel and the CSV import (owner decision H, BUILD_PLAN.md C29 — no separate import script), so for launch: `mysqldump` the local DB → import on cPanel (phpMyAdmin), and zip `UPLOAD_DIR/media` → extract on the host.
6. **Staging smoke test right after purchase:** sharp works (image upload), login, order, proof upload, restart, the six security headers present, and `sessions.ip` showing a real address (the rate limits key on the last `X-Forwarded-For` entry and fall back to `unknown`, SEC-15; DEPLOY.md §7). Things to confirm with the host: Node 20.9+, glibc ≥ 2.26, the upload body limit (≥ 6 MB), and whether Passenger's `listen()` hook works with the standalone server.
7. **Backups:** a daily cPanel cron running `mysqldump`, and a periodic copy of `UPLOAD_DIR`.
8. Logging: `console.error` goes to Passenger's stderr log. `src/instrumentation.ts` (`onRequestError`, S22) logs each unhandled request error once with method, path and digest, never a body or cookie. Friendly boundaries: `app/global-error.tsx`, `app/not-found.tsx`, `(store)/error.tsx`, `panel/(protected)/error.tsx` and `not-found.tsx` (rendered inside the panel frame).
